# Нестабильная загрузка фотографий при переключении удостоверений

Дата: 2026-07-20
Ветка: `refactor/backend-architecture`
Страница: `/certificates`

## Краткий итог

Причина подтверждена тестом и сетевыми логами: **брошенные загрузки фотографий
никогда не отменялись**. При переключении записей быстрее, чем успевают
скачиваться фото, каждое покинутое изображение продолжало занимать соединение, и
актуальное фото оказывалось в очереди позади всех предыдущих — вплоть до того,
что ответ по нему не приходил вовсе.

Исправление — одна строка в `usePhotoImage`: cleanup-функция эффекта теперь
обрывает загрузку через `image.src = ''`.

Статус: **исправлено и проверено локально. Через `https://internal.avku.org` не
проверено** — см. раздел «Что осталось непроверенным».

---

## 1. Сценарий воспроизведения

Автоматизирован в `apps/web/e2e/certificates-photo-switching.spec.js`:

1. Открыть `/certificates`.
2. Последовательно переключить 20 записей с интервалом 150 мс.
3. Повторить быстрый прогон 3 раза.
4. После каждого прогона проверить, что в кадрирующей рамке загружено фото
   именно последней выбранной записи (`naturalWidth > 0` и `src` содержит имя
   файла этой записи).
5. Вернуться к первой записи и проверить её фотографию.

Задержка ответов задаётся тремя уровнями пропускной способности через CDP
(`Network.emulateNetworkConditions`), подобранными так, чтобы типовое превью
~200 КБ скачивалось примерно за 300 мс, 1 с и 3 с.

**Почему троттлинг, а не `page.route()`.** Перехват с `route.fulfill()` отдаёт
тело из драйвера Playwright и немедленно освобождает сокет — это уничтожает
ровно тот механизм, который исследуется (пул соединений браузера). Троттлинг
оставляет каждую загрузку на настоящем сокете, поэтому брошенная закачка
удерживает соединение так же, как у оператора на медленном туннеле.

## 3. Подтверждённая причина

`apps/web/src/features/certificates/usePhotoImage.js`

Cleanup-функция эффекта снимала обработчики:

```js
return () => {
  isCurrent = false;
  image.onload = null;
  image.onerror = null;
};
```

Этого достаточно, чтобы устаревший ответ не был **применён** к состоянию, но сама
HTTP-загрузка продолжалась до конца и удерживала соединение. Хук вызывается из
двух мест (`PhotoCropper` и `CertificatePreview`), браузер дедуплицирует их в
один запрос на URL — то есть на каждое переключение оставался жить один
неотменённый запрос.

Пока фото скачивались быстро (локальная сеть, ~2 мс), эффект был незаметен. На
медленном канале 15–20 переключений оставляли до 18 одновременных загрузок; при
лимите HTTP/1.1 в 6 соединений на origin актуальное фото вставало в конец
очереди и не получало полосы.

Это объясняет все три описанных симптома — пустой блок, зависшее состояние
загрузки и сообщение об ошибке (по таймауту), — и то, почему обновление страницы
временно восстанавливает работу.

## 4. Исключённые гипотезы

| Гипотеза | Вывод | Основание |
|---|---|---|
| Rate limit nginx (общий IP cloudflared) | **Исключена** | Лимитер реально отдаёт 503 (воспроизведено принудительно: 95 из 150 запросов). Но за всё доступное окно логов все 95 событий `limiting requests` и все 503 принадлежат этому тесту (`User-Agent: curl`). Реальный трафик за то же окно — 122 запроса фото, все 200. Оговорка: логи старше рестарта контейнера (2 ч) утрачены. |
| `curl -I` → 404 | **Исключена как причина** | Подтверждено: маршрут в `apps/api/src/routes/certificates.ts:293` проверяет `request.method === "GET"`, HEAD не поддержан. Браузер грузит изображения через GET, к дефекту отношения не имеет. |
| Ошибки sharp / зависшие Promise / кэш превью | **Исключена** | 25 фото последовательно и 25-ю параллельно — 100 % ответов 200, корректные `Content-Length` (21–333 КБ). Повторные запросы 1.5–3 мс, то есть LRU-кэш работает. Ошибки в `apps/api/src/server.ts:136` всегда завершаются ответом, «вечный pending» на стороне API невозможен. |
| Cloudflare QUIC timeout | **Не подтверждена и не требуется** | Проблема полностью воспроизводится на локальном nginx, без участия туннеля. Совпадений по времени не искали, так как причина найдена ниже по стеку. |
| Повторное добавление `?w=` | **Исключена** | `getPhotoPreviewUrl` вызывается один раз в мемоизированном `useMemo` (`CertificatesPage.jsx:202`); покрыто юнит-тестом. |
| Гонка «старое/новое изображение», несоответствие фото записи | **Исключена** | Проверка в тесте: ни одного запроса фото для невыбранной записи; возврат к первой записи показывает её собственное фото. Guard `isCurrent` в хуке корректен. |

Замечание: в коде `PHOTO_PREVIEW_WIDTH = 1200`, а не 800, как указывалось в
постановке задачи (`apps/web/src/features/certificates/certificateTypes.js:25`).

## 5. Внесённое исправление

```js
return () => {
  isCurrent = false;
  image.onload = null;
  image.onerror = null;
  image.src = '';   // обрывает загрузку, освобождая соединение
};
```

Обработчики снимаются до сброса `src`, поэтому обрыв не может вызвать `onerror`.

Правка минимальна и намеренно не трогает ни API, ни nginx: конфигурация
rate limit оставлена как есть, поскольку доказательств её причастности нет.

### Две помехи, устранённые по ходу перепроверки

Обе — артефакты окружения, к дефекту отношения не имеют, но обе ломали прогон.

1. **`apps/web/dist/` принадлежал `root`** (остаток запуска контейнера от root).

   `@esbuild+linux-x64` и `@img+sharp-linux-x64`, тесты дали 53/53.

   Production этим не затронут: образ `avku-internal-api` ставит зависимости
   внутри Linux на этапе сборки. Дефект был только в хостовой рабочей копии.

Регрессионный тест проверен на неполноту: фикс временно откатывался, образ

## 8. Проверка локально и через Cloudflare

**Локально (`http://192.168.0.151:18080`): проверено.** Образ web пересобран,
контейнер перезапущен, E2E 4/4 зелёные против реального nginx.

**Через `https://internal.avku.org`: НЕ проверено.** Перепроверено 2026-07-20:
`GET /certificates` → `302` на `avku.cloudflareaccess.com`, в meta-токене
`auth_status: NONE`; `GET /api/certificates` → тоже `302`. Требуется
интерактивный вход через IdP, невозможный в неинтерактивной сессии.

Прогон через туннель оформлен отдельным файлом
`e2e/certificates-photo-switching.cloudflare.spec.js`. Без
`AVKU_E2E_STORAGE_STATE` он **пропускается** с указанием, что именно нужно
сделать (проверено: `1 skipped`, exit 0) — красный прогон не должен означать
«никто не залогинился». Помимо инварианта отмены он проверяет отсутствие
статусов ≥ 400 и ошибок в консоли браузера — то, что имеет смысл мерить только
за реальным edge.

Инфраструктура для этой проверки готова — конфиг читает `storageState` из
переменной окружения. Порядок:

```bash
# 1. Один раз войти вручную и сохранить сессию ВНЕ репозитория
cd apps/web
npx playwright open --save-storage=$HOME/.avku-access.storageState.json \
  https://internal.avku.org/certificates

# 2. Прогнать E2E через туннель
AVKU_E2E_BASE_URL=https://internal.avku.org \
AVKU_E2E_STORAGE_STATE=$HOME/.avku-access.storageState.json \
npx playwright test --project=chromium
```

`storageState` — носитель сессии; хранить строго вне репозитория. `.gitignore`
дополнительно закрывает `**/*.storageState.json` и `apps/web/.auth/`.

Ожидание: через туннель канал медленнее, поэтому до исправления симптом должен
проявляться сильнее, а после — тесты должны быть зелёными. **Это ожидание, а не
измерение.** Считать проблему устранённой в production до прогона по инструкции
выше нельзя.

- Исправление присутствует в исходном коде (`usePhotoImage.js:82`) и в собранном
  бандле; хеш бандла совпадает с тем, что отдаёт локальный nginx.
- Frontend unit — 19/19; API — 53/53; локальные E2E — 4/4; сборка frontend.
- Установленные зависимости совпадают с lock-файлом (`Already up to date`).
- `node_modules` не отслеживается Git (`git ls-files | grep -c node_modules` → 0);
  в `apps/web/node_modules` нет Windows-артефактов и битых симлинков.
- `apps/api/node_modules` был Windows-установкой — переустановлен на Linux.
- `.gitignore` содержит `**/*.storageState.json`; ни одного файла
  `storageState` в индексе Git нет.
- Cloudflare-спека корректно пропускается без переменной окружения.
- Аудит хука и смежных компонентов по коду (раздел 7a).

### Не проверено

- **Production через `https://internal.avku.org`** — блокирует Cloudflare Access
  (302 на IdP, `auth_status: NONE`). Нужен интерактивный вход и сохранённый
  `storageState`.
- **Деплой не выполнялся** — новая сборка в production не раскатана.
- Ручное переключение 15–20 удостоверений в браузере оператора за туннелем,
  отсутствие 404/503 и ошибок консоли в production — всё это следствия
  предыдущих двух пунктов.
- Отдельного прогона E2E «до исправления» в этой сессии не делалось;
  результат «2 failed» взят из более раннего прогона.

### Вывод

Локальные проверки зелёные и подтверждают готовность правки к деплою. Считать
production исправленным нельзя до тех пор, пока новая сборка не раскатана и
проверка через `https://internal.avku.org/certificates` не пройдена.
