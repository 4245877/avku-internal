## 1. Краткий вывод о текущем состоянии

**Раздел «Вибори» — это качественно сделанный картографический просмотрщик OSM без
серверной части и без предметной модели избирательной кампании.**

Три факта определяют всё остальное:

1. **Данных кампании в проекте нет вообще.** В `apps/api` существует ровно один
   маршрут — `/api/elections/area`, который хранит один GeoJSON-полигон границы
   рабочей территории в файле. Ни одной таблицы БД, относящейся к выборам, не
   существует: `apps/api/src/db/sqlite.ts` не содержит ни одного `CREATE TABLE`
   для этого модуля, а `.sql`-миграций в проекте нет в принципе (миграции здесь
   пишутся инлайн в TS — см. `warehouse-records.ts:535`).

2. **Вся введённая пользователями работа живёт в `localStorage` одного браузера.**
   Ключ `avku-elections-details-v1`,
   [electionsApi.js:49](apps/web/src/features/elections/electionsApi.js#L49).
   Это подтверждено и в README:1408 — «there is no API persistence yet». Данные
   не видны коллегам, не резервируются, теряются вместе с профилем браузера, и
   стираются кнопкой в шапке страницы без подтверждения.

3. **Ветка `backend` — нерабочая заглушка, выглядящая как реализация.**
   `VITE_ELECTIONS_SOURCE=backend` заставляет клиент обращаться к `GET /houses` и
   `PATCH /houses/:id/details`
   ([electionsApi.js:237](apps/web/src/features/elections/electionsApi.js#L237),
   [:443](apps/web/src/features/elections/electionsApi.js#L443)). **Этих
   маршрутов в `apps/api` не существует.** Переключение источника сегодня
   означает не «включить бэкенд», а «сломать раздел».

При этом собственно карта сделана хорошо и её надо сохранять: 5 896 реальных
зданий OSM, каждое — отдельный кликабельный полигон на общем canvas-рендерере,
корректная работа с темами, редактор границы территории с честной валидацией
полигона на сервере и продуманная логика покрытия датасета. Это не прототип, это
рабочая основа.

**Главный вывод:** задача не в том, чтобы «доработать раздел», а в том, чтобы
**построить под уже существующим хорошим интерфейсом отсутствующий фундамент** —
серверную модель данных с кампаниями, людьми, действиями и историей — и при этом
удалить одну функцию, которой там быть не должно (см. §4.1).

## 4. Ошибки и ограничения текущей модели данных

### 4.1. Критично: персональное политическое профилирование

Модель `Resident` хранит **поимённо, с номером квартиры, политическую позицию
конкретного жителя**:

```js
// apps/web/src/features/elections/electionsTypes.js:180-189
{ id, name, apartment, stance: 'support'|'neutral'|'against'|'unknown', ageGroup, note }
```

- вводится в [ResidentsFieldset.jsx:87-101](apps/web/src/pages/ElectionsPage/components/ResidentsFieldset.jsx#L87)
  (выпадающий список «Позиція»: Підтримує / Нейтрально / **Проти**);
- агрегируется в [houseUtils.js:120-132](apps/web/src/features/elections/houseUtils.js#L120)
  (`getStanceBreakdown` — счётчик сторонников и противников по дому);
- отображается в [HouseSummary.jsx:244-280](apps/web/src/pages/ElectionsPage/components/HouseSummary.jsx#L244)
  сводкой по дому и карточками жителей с подсветкой позиции.

**Это ровно та функция, которую запрос запрещает** («не создавай скрытые рейтинги
жителей, прогнозы политических взглядов или инструменты персонального
профилирования»). Дополнительно:

- политические взгляды — особая категория персональных данных (GDPR ст. 9,
  ЗУ «Про захист персональних даних» ст. 7); их обработка требует отдельного
  правового основания, которого у полевого обхода нет;
- хранится **в `localStorage` в открытом виде**, без шифрования, без контроля
  доступа, на устройстве, которое ходит по домам;
- любой, кто получит устройство, получает поимённый список политических
  противников с адресами и номерами квартир.

**Решение (P0):** удалить `stance` и `ageGroup` из модели человека. Оставить
контактное лицо (староста, глава ОСББ, консьерж) с ролью и контактом — это
законная и нужная сущность. Отношение к кампании фиксировать **на уровне дома и
обезличенно**, если это вообще нужно, а не на уровне человека.

### 4.2. Одна запись содержит пять разных сущностей

`HouseDetails` ([electionsTypes.js:204-220](apps/web/src/features/elections/electionsTypes.js#L204))
одновременно держит:

| Что лежит | Чем на самом деле является |
|---|---|
| `entrances`, `apartments`, `residentsCount`, `householdsCount` | постоянные характеристики дома |
| `canvassStatus`, `priority`, `surveyedAt` | состояние работы в конкретной кампании |
| `residents[]` | люди (отдельная сущность) |
| `contacts[]` | контакты (принадлежат человеку, а не дому) |
| `notes`, `accessNote` | свободный текст, в котором тонут обращения, задачи и договорённости |

Это именно та «одна перегруженная таблица», которой запрос велит избежать.
Практические следствия:

- **вторая кампания затирает первую** — `canvassStatus` один на дом, истории нет;
- **человек привязан к дому намертво** — переезд, тот же человек в двух домах,
  контакт по подъезду не выражаются;
- **договорённость из `notes` не превращается в задачу** — её никто не увидит в
  списке дел и никто не заметит просрочку.

### 4.3. Идентификатор дома нестабилен

`house.id` — это OSM-идентификатор (`way/180170140`,
[electionsTypes.js:51](apps/web/src/features/elections/electionsTypes.js#L51)), и
он же ключ оверлея правок ([electionsApi.js:460](apps/web/src/features/elections/electionsApi.js#L460)).

OSM-way не является стабильным идентификатором: при перерисовке здания,
разделении контура или удалении объекта маппером id меняется. При следующем
`pnpm data:houses` вся работа по такому дому **молча осиротеет** — оверлей
останется, дом с новым id будет пустым, и никто об этом не узнает.

Нужен собственный первичный ключ дома, а `osm_type`/`osm_id` — как атрибут
сопоставления (не уникальный, допускающий смену).

### 4.4. Кампании как измерения не существует

Штаб захардкожен в исходниках в двух местах:

- [geo.js:24](apps/web/src/features/elections/geo.js#L24) — `AREA_CENTER` с адресом
  «вулиця Зодчих, 58А»;
- [osmBuildings.js:31](apps/web/src/features/elections/osmBuildings.js#L31) —
  `HEADQUARTERS_OSM_ID = 'way/180170140'`.

Сменить кампанию, округ или штаб сегодня можно только правкой кода и
пересборкой. Сохранить историю прошлой кампании невозможно в принципе.

### 4.5. Отсутствие авторизации

[access-auth.ts:18-22](apps/api/src/http/access-auth.ts#L18): «A request with no
JWT is treated as trusted local (LAN) access». Маршрут выборов идентичность
получает, но **не проверяет** — `employee` используется только для подстановки в
`updatedBy` ([elections.ts:60](apps/api/src/routes/elections.ts#L60)).

Следствие: любой в локальной сети может `PUT` или `DELETE` границу рабочей
территории — то есть **изменить для всех сразу, какие дома вообще существуют**
(граница фильтрует датасет, [electionsApi.js:368](apps/web/src/features/elections/electionsApi.js#L368)).
Ролей нет ни в каком виде.

### 4.6. Прочее

- **Потеря данных встроена в архитектуру.** Чистка данных браузера = потеря всей
  работы. Резервных копий нет, потому что нечего копировать.
- **Масштабирование.** Весь датасет (4,7 МБ JSON) загружается целиком в память
  клиента при каждом открытии страницы, фильтрация и сортировка — на клиенте
  ([houseUtils.js:281](apps/web/src/features/elections/houseUtils.js#L281)). Для
  5 896 домов приемлемо; для города или нескольких кампаний — нет.
- **Оценки смешиваются с фактами в сводке.** `summary.residents` суммирует
  геометрические оценки наравне с замерами
  ([houseUtils.js:327](apps/web/src/features/elections/houseUtils.js#L327)) и
  показывается в шапке как «Мешканців, орієнтовно». Подпись честная, но на
  дашборде такое число легко принять за факт.
- **Нет мягкого удаления и нет контроля массовых операций** — единственная
  массовая операция сегодня это «стереть всё».

## 5. Рекомендуемая структура сущностей и связей

Принцип: **дом остаётся единственным объектом на карте; всё изменяемое —
отдельные записи, привязанные к паре (дом, кампания).**

```
campaigns ──┬─< house_campaign_state >── houses ──< house_attachments
            │                              │
            │                              ├──< house_people >── people ──< person_contacts
            │                              └──> precincts
            ├─< assignments (кто отвечает за дом/участок в кампании)
            ├─< actions        (журнал: звонок, визит, встреча)
            ├─< issues         (обращения и проблемы)
            ├─< tasks          (что нужно сделать)
            ├─< events         (встречи, палатки, временные точки)
            ├─< shifts ──< shift_members
            └─< material_issues ──> warehouse_items (существующий модуль)

change_log  — сквозной журнал изменений по всем таблицам
import_batches ──< import_rows  — промежуточная область импорта
```

### 5.1. Постоянные характеристики дома — `houses`

Не зависит от кампании. Меняется редко.

| Поле | Тип | Примечание |
|---|---|---|
| `id` | TEXT PK | **собственный** UUID, не OSM |
| `osm_type`, `osm_id` | TEXT / INTEGER | сопоставление с OSM, **не** уникальный ключ |
| `precinct_id` | TEXT FK → `precincts` | избирательный участок |
| `street`, `number` | TEXT NOT NULL | нормализованные |
| `address_normalized` | TEXT | ключ для поиска дублей, генерируется |
| `lat`, `lon` | REAL NOT NULL | CHECK по диапазонам |
| `footprint` | TEXT (JSON) | контур |
| `type`, `building`, `floors`, `built_year`, `footprint_area_sqm` | | из OSM |
| `entrances`, `apartments` | INTEGER | **подтверждённые** значения; оценки не хранить — вычислять |
| `source` | TEXT NOT NULL | `osm` / `import:<batch>` / `manual` |
| `verified_at`, `verified_by` | TEXT | дата и автор последней проверки |
| `deleted_at` | TEXT NULL | мягкое удаление |

Индексы: `UNIQUE(osm_type, osm_id) WHERE osm_id IS NOT NULL`,
`UNIQUE(address_normalized) WHERE deleted_at IS NULL`, `(precinct_id)`, `(lat, lon)`.

**Почему:** разделяет «дом такой» и «по дому сделано столько-то». Позволяет вести
несколько кампаний без копирования домов.

### 5.2. Состояние работы — `house_campaign_state`

Одна строка на пару (дом, кампания). **Это и есть ответ на вопрос «как сохранить
историю разных кампаний без копирования домов».**

| Поле | Примечание |
|---|---|
| `house_id`, `campaign_id` | PK (составной) |
| `stage` | справочник этапов: `not_started` / `in_progress` / `done` / `refused` |
| `priority` | `high` / `medium` / `low` |
| `last_action_at`, `last_action_id` | **вычисляется** триггером из `actions`, не вводится |
| `open_issues_count`, `overdue_tasks_count` | **вычисляется**, не вводится |
| `data_quality` | вычисляется из полноты и свежести `verified_at` |

### 5.3. Люди — `people`, `person_contacts`, `house_people`

- `people`: `id`, `full_name`, `role` (справочник: староста, голова ОСББ,
  консьерж, активіст…), `notes`, `source`, `deleted_at`.
  **Без `stance`. Без `ageGroup`.**
- `person_contacts`: `person_id`, `type`, `value`, `value_normalized` (для поиска
  дублей по телефону), `is_primary`.
- `house_people`: `house_id`, `person_id`, `entrance`, `apartment`, `role_in_house`,
  `valid_from`, `valid_to` — закрепление как связь, а не как поле дома.

**Почему:** один человек может отвечать за два подъезда или переехать; телефон
принадлежит человеку, а не стене.

### 5.4. Журнал работы — `actions`

Основная рабочая таблица. `id`, `campaign_id`, `house_id` (NULL), `person_id`
(NULL), `type` (`call` / `visit` / `meeting` / `material` / `note`), `result`
(справочник: `contacted` / `no_answer` / `refused` / `scheduled`), `happened_at`,
`author_id`, `comment`, `attachment_id`.

**Почему:** «что было сделано последним» и «когда мы тут были» — вопросы, на
которые сегодня отвечает свободный текст в `notes`. Отсюда же считается
`last_action_at` и активность по сотрудникам.

### 5.5. Остальные сущности

| Таблица | Ключевые поля | Зачем |
|---|---|---|
| `campaigns` | `id`, `name`, `starts_on`, `ends_on`, `hq_house_id`, `area_geojson`, `status` (`active`/`archived`) | Ось всей работы. Убирает захардкоженный штаб. Архивация кампании = смена `status`. |
| `precincts` | `id`, `number`, `district`, `boundary_geojson`, `address` | Фильтрация по участку и округу. |
| `assignments` | `campaign_id`, `scope` (`house`/`precinct`), `scope_id`, `employee_id`, `role`, `valid_from/to` | **Несколько ответственных** и поиск домов без ответственного. |
| `issues` | `campaign_id`, `house_id`, `category` (справочник), `title`, `status`, `opened_at`, `closed_at`, `assignee_id` | Обращения и проблемы жителей. |
| `tasks` | `campaign_id`, `house_id?`, `title`, `due_at`, `status`, `assignee_id` | Просрочки и «дела на сегодня». |
| `events` | `campaign_id`, `type` (`meeting`/`tent`/`other`), `lat`, `lon`, `starts_at`, `ends_at`, `house_id?` | Встречи, палатки и временные точки — **точки на карте, но не дома**. |
| `shifts`, `shift_members` | `campaign_id`, `event_id?`, `starts_at`, `ends_at`, `employee_id` | Смены и календарь. |
| `material_issues` | `campaign_id`, `warehouse_item_id`, `quantity`, `issued_to`, `issued_at` | Выдача материалов **через существующий склад**, без дублирования номенклатуры. |
| `house_attachments` | `house_id`, `campaign_id`, `file_path`, `kind`, `uploaded_by` | Фото подъезда, доски объявлений. Хранение — по образцу `storage/certificates/photos`. |
| `change_log` | `table_name`, `row_id`, `field`, `old_value`, `new_value`, `changed_by`, `changed_at` | История изменений, разбор конфликтов, откат. |
| `import_batches`, `import_rows` | см. §9 | Промежуточная область импорта. |

**Справочники** (`stage`, `priority`, `action_type`, `action_result`,
`issue_category`, `person_role`, `contact_type`) — отдельными таблицами или
CHECK-константами, но **в одном месте**, разделяемом клиентом и API. Сегодня они
живут только в клиентском `electionsTypes.js` и на сервере не валидируются.

### 6.2. Правила разбора старых записей

**Переносить как есть:** адрес, координаты, количество подъездов и квартир,
статус обхода, приоритет, дата обхода, имя и роль контактного лица, телефон.

**Преобразовывать:**

| Было | Станет |
|---|---|
| `residents[].name/apartment` | запись в `people` + связь `house_people` |
| `contacts[]` | `person_contacts`, привязанные к человеку, а не к дому |
| `notes` — «просили полагодити освітлення» | `issues` (обращение) |
| `notes` — «передзвонити у вівторок» | `tasks` (задача со сроком) |
| `notes` — «заходив 12.05, не відчинили» | `actions` (действие с результатом `no_answer`) |
| `notes` — «домофон 45В, консьєрж до 18:00» | `houses.access_note` (постоянная характеристика) |
| `updatedBy` (свободный текст) | сопоставить с `employees` по имени; несопоставленное — в `change_log` как исторический комментарий, **не** в поле автора |
| `surveyedAt` | `actions.happened_at` первого визита + `verified_at` |

**Не переносить в основную систему:**

- `stance` и `ageGroup` жителей — **исключить полностью** (§4.1). Если нужна
  историческая справка — только обезличенный агрегат по дому в архивной таблице
  вне рабочего интерфейса, и лучше не хранить вовсе;
- геометрические оценки `estimate.*` — вычислять;
- кадровые, юридические и финансовые сведения, паспортные данные, сведения о
  судимости, партийные документы, подписи и выплаты — в модуле выборов им не
  место ни в каком виде;
- свободные оценочные суждения о жителях («скандальна бабця») — не переносить.

**В архив (только чтение, вне рабочего интерфейса):** сырые импортированные
строки в `import_rows` с исходным текстом — чтобы можно было вернуться к
первоисточнику, не тащя мусор в рабочие таблицы.

## 7. Предлагаемая структура карты и карточки дома

### 7.1. Цвет и признаки маркера

**Цвет = этап работы по дому в текущей кампании, и только он.** Пять состояний,
пять цветов: не начато / в работе / обойдено / отказ / недоступно.

Остальное — **отдельными накладными признаками**, не смешиваясь с цветом:

| Признак | Как показать |
|---|---|
| Просроченная задача или открытое обращение | красная точка-бейдж в углу контура |
| Высокий приоритет | утолщённая обводка |
| Нет ответственного | пунктирная обводка |
| Данные не проверялись > 30 дней | пониженная непрозрачность заливки |
| Штаб | отдельная иконка (как сейчас) |

**Почему:** сегодня цвет кодирует заполненность формы — показатель
административный, а не рабочий. Координатору нужно видеть «где мы ещё не были»,
а не «где не дописан текст в поле нотаток».

### 7.2. Подсказка при наведении/долгом нажатии

Пять строк, не больше:

```
вул. Зодчих, 58-А
Дільниця №123 · 4 під'їзди · 128 квартир
Етап: в роботі · Пріоритет: високий
Відповідальний: Коваленко О.
Останнє: візит 28.07 · ⚠ 1 прострочена задача
```

Обязательно продублировать на долгое нажатие — сейчас на тач-устройствах
подсказки нет вообще.

### 7.3. Боковая карточка дома — вкладки

| Вкладка | Содержимое |
|---|---|
| **Огляд** | адрес, участок, этап, приоритет, ответственные, качество данных («перевірено 12.07, Коваленко О.»), характеристики дома, последнее действие, следующее действие |
| **Люди** | контактные лица с ролями и телефонами, кнопка звонка. **Без позиций и возрастов.** |
| **Дії** | хронологический журнал: звонки, визиты, встречи, выдача материалов |
| **Звернення** | открытые и закрытые обращения с категориями и сроками |
| **Задачі** | задачи по дому со сроками и исполнителями |
| **Файли** | фото и вложения |
| **Історія** | журнал изменений полей: кто, когда, что было, что стало |

### 7.4. Быстрые действия — одна строка кнопок в шапке карточки

`Дзвінок` · `Візит` · `Звернення` · `Задача` · `Фото` · `Коментар`

Каждая — одно модальное окно на 2–3 поля, закрывается за 5 секунд. Это главный
сценарий полевой работы: человек стоит в подъезде, а не сидит за столом.
Приоритет — выше, чем у полной формы редактирования.

### 7.5. Что убрать из карточки

- блок «Мешканці» с позициями и возрастами (§4.1);
- сводку «Підтримує: 3 · Проти: 1»;
- поле `updatedBy` как вводимое вручную — заполнять из идентичности.

## 8. Необходимые фильтры, функции и рабочие сценарии

Для каждой — какую задачу решает. Функции «для количества» в список не включены.

### 8.1. Обязательные (P1)

| Функция | Какую проблему решает |
|---|---|
| Фильтр по этапу работы | «Куда идти сегодня» — сейчас невозможно получить список необойдённых домов |
| Фильтр по приоритету | Поле есть, фильтра нет — приоритет бесполезен |
| Фильтр по ответственному | Агитатор не может увидеть только свои дома |
| Фильтр по участку и округу | Работа планируется по участкам, а не по улицам |
| Поиск по телефону | По номеру найти, чей это контакт и в каком доме — сейчас индексируется только адрес |
| Поиск по ответственному | Передача дел, замена заболевшего |
| «Дома без ответственного» | Главная дыра в покрытии территории; сейчас невидима |
| «Просроченные задачи» | Без этого задачи не работают как инструмент |
| «Дела на сегодня» | Стартовый экран агитатора |
| Мобильный ввод результата визита | Ввод в поле, а не переписывание вечером — главный источник потерь данных |

### 8.2. Управление кампанией (P2)

| Функция | Какую проблему решает |
|---|---|
| Массовое назначение домов | Раздать участок бригаде за одну операцию, а не 200 кликов. **С подтверждением и записью в `change_log`.** |
| Календарь встреч и смен | Кто где сегодня работает |
| Объединение дублей | Импорт из разных файлов неизбежно даст дубли |
| Журнал изменений | Разбор «кто стёр данные по дому» |
| Экспорт с контролем | Отчётность. **Без персональных данных по умолчанию**, с записью в журнал экспорта |
| Архивирование кампании | Закрыть кампанию, сохранив данные и освободив рабочий интерфейс |

### 8.3. Дополнительно (P3)

| Функция | Какую проблему решает | Оговорка |
|---|---|---|
| Дашборд: покрытие, активность, обращения, просрочки, качество данных | Управленческая картина | Только агрегаты по территории, **не по жителям** |
| Построение маршрута по домам | Экономия времени обхода | Нужен только если обход идёт пешими маршрутами; иначе не строить |
| Офлайн-работа с синхронизацией | Подвалы и лифты без связи | Дорого. Делать **только после** того, как онлайн-ввод заработает и станет ясно, что связь реально мешает |

## 9. Рекомендации по импорту и очистке старых данных

**Прямой импорт старых таблиц в рабочие таблицы недопустим.** Схема:

```
файл → import_batches / import_rows → предпросмотр и проверка → рабочие таблицы
                    (сырой текст)        (человек подтверждает)
```

### Этапы

1. **Загрузка.** Файл целиком пишется в `import_rows` как есть: одна строка
   файла — одна запись, исходный текст сохраняется навсегда. Ничего не
   нормализуется.

2. **Нормализация в предпросмотре, не в базе:**
   - адрес → `address_normalized` (единый формат «вул. X, N», раскрытие
     сокращений, единый апостроф — механизм уже есть в
     [streetNames.js](apps/web/src/features/elections/streetNames.js) и
     [houseUtils.js:21](apps/web/src/features/elections/houseUtils.js#L21));
   - телефон → E.164;
   - координаты → проверка попадания в границу кампании; выпавшие — на ручной
     разбор, **не отбрасывать молча**.

3. **Проверка дублей** по трём ключам: `address_normalized`, `(osm_type, osm_id)`,
   нормализованный телефон человека. Каждая пара показывается рядом с
   предложением «создать / объединить / пропустить». Решение принимает человек.

4. **Разбор свободного текста** по §6.2: строки `notes` предлагаются к
   преобразованию в обращения, задачи или действия — с ручным подтверждением
   категории. Автоматическую классификацию не делать.

5. **Применение.** Только после подтверждения, одной транзакцией, с записью
   `source = 'import:<batch_id>'` в каждую созданную строку и полной записью в
   `change_log`. Импорт должен быть **обратимым**: по `batch_id` можно откатить.

6. **Отчёт по партии:** создано / объединено / пропущено / требует внимания.

**Чего не делать:** не импортировать поля с политическими позициями, даже «на
время»; не создавать дома из строк без координат и без распознанного адреса; не
доверять дате из файла как `verified_at`, если в файле нет автора проверки.

### 10.2. Обязательные меры

| Мера | Почему |
|---|---|
| **Проверка роли в `handleElectionsRequest`** | Сейчас границу территории может стереть любой в LAN (§4.5) |
| **Убрать «trusted local access» для операций записи** | Отсутствие JWT не должно означать полные права |
| **Автор из идентичности, а не из формы** | `updatedBy` сегодня — свободный текст (§2.2) |
| **Мягкое удаление везде** | `deleted_at` вместо `DELETE`; ничего не пропадает бесследно |
| **Подтверждение и лимит на массовые операции** | «Скинути демо-дані» сегодня стирает всё без вопроса |
| **Скрытие персональных данных по умолчанию** | Телефоны и имена — только тем, кому назначен дом; в списках и экспорте — маскировать |
| **Журнал просмотров и экспорта** | Утечка базы контактов должна быть отслеживаемой |
| **Экспорт без персональных данных по умолчанию** | Полный экспорт — отдельное право и отдельная запись в журнале |
| **Кадровые, юридические, финансовые данные — вне модуля** | Они не должны попадать в карточку дома ни при каких условиях |

### 10.3. Что удалить

Политические позиции жителей — из модели, интерфейса и уже сохранённых
`localStorage` (§4.1). Это не «понизить приоритет», это условие P0.
